# Version-bump release checklist — make publishing X.Y.Z mechanical

Companion to [PUBLISH.md](../../PUBLISH.md) ("Immutable-version discipline"). Built
2026-10-16 from the actual 0.1.0 → 0.1.2 release history, including the two traps
hit on 0.1.2. Follow top to bottom; every step has an exact command and expected
output. Do not skip steps to "save time" — the registry rejects mistakes
permanently (versions are unique per publish, metadata is immutable).

## The 8 version-bearing surfaces (the complete list)

| # | File | Field | Who reads it |
|---|---|---|---|
| 1 | `src/version.ts` | `export const version = "X.Y.Z"` | server banner, MCP `serverInfo`, report preamble (`_Generated by research-scope-mcp X.Y.Z_`) |
| 2 | `package.json` | `"version"` | npm (dry-run/publish), badge |
| 3 | `server.json` | `"version"` | official MCP registry (`mcp-publisher publish` reads it) |
| 4 | `CHANGELOG.md` | new `## [X.Y.Z] — YYYY-MM-DD` section | humans; Glama "maintenance" grade |
| 5 | `README.md` | any version visible in install/verify snippets | buyers, directory scrapes |
| 6 | demo players (`docs/marketing/demo-60s/demo.html`, `demo-vertical.html`, `demo-setup-vertical.html`) | `.sub` lines, outro, footer | the $9 Starter kit + shorts viewers (screenshot provenance) |
| 7 | **npm pending caveat** (`CHANGELOG` "### Pending" + `docs/publication/npm-status-followup-comments.md`) | carries the *previous* release's npm state per version | the open Cline/mcp.so issue threads |
| 8 | agent-side ledger (`gumroad-tracks/trackC-mcp-kit.md` §2) | publish log rows | session continuity |

Cosmetic-but-frozen (never auto-bump these): `run-capture.jsonl` (sha-pinned
transcript — bumping the version invalidates the capture), `demo-plan.md` scene
table, anything inside `docs/publication/*` comment drafts that cite a live
published version — those describe *shipped* versions, update only after the
registry actually has the new one.

## Pre-flight (5 min)

```bash
cd /Users/agent/Projects/research-scope-mcp
git status --short                 # clean tree, or commit first — never bump on a dirty tree
git log --oneline -3               # know what you're releasing
```

- Working tree clean of *your* changes (pre-existing unrelated edits may stay
  untouched, they just don't ride this commit).
- Decide the new version: **fix → patch bump**, feature → minor, breaking →
  major. Registry rule: never re-publish the same X.Y.Z.

## Step 1 — bump the code triple (2 min)

All three in one str_replace-style pass, then verify:

```bash
sed -n '1p' src/version.ts         # edit to: export const version = "X.Y.Z";
grep '"version"' package.json      # edit to: "version": "X.Y.Z",
grep '"version"' server.json       # edit to: "version": "X.Y.Z",
```

Cross-check nothing was missed (run with OLD and NEW version substituted;
OLD must print 0 hits, NEW must print exactly 3):

```bash
grep -rn '"OLD"' src/version.ts package.json server.json   # expect: no matches
grep -rn '"NEW"' src/version.ts package.json server.json   # expect: exactly 3 lines
grep -rn 'export const version' src/version.ts             # sanity: the export line
```

## Step 2 — CHANGELOG: write the section BEFORE any publish attempt (5 min)

New `## [X.Y.Z] — <today>` at the top. Rules learned from 0.1.2:

- Write only what's **in the diff you will commit**. Nothing aspirational.
- **⚠ Trap #1 (hit on 0.1.2):** the first release commit pre-wrote
  "first npm publication" into the CHANGELOG before `npm publish` was attempted —
  npm turned out ENEEDAUTH-blocked and a correction commit was needed
  (`d574931`). **Never write a pending claim as a past-tense fact.** Put it
  under `### Pending` in future tense with the exact unblock condition:
  *"publishes as soon as an npm account/token is attached"*.
- If npm goes live same-day, fine — but only rewrite the Pending block into
  past tense *after* `npm publish` exits 0.
- Registry publication claim likewise: write "scheduled with this version" until
  `mcp-publisher publish` has succeeded.

## Step 3 — build + test (3 min, mandatory gate)

```bash
npm test                           # runs tsc + node --test test/server.test.mjs
```

Expect: `# pass 3` / `# fail 0` (or the current test count — it grows at 0.1.3+).
The live-network fetch test needs outbound net; if it fails on network, fix the
cause, never skip. Then the banner spot-check (proves surfaces #1 chain):

```bash
node dist/index.js --help 2>&1 | head -3   # banner prints research-scope-mcp X.Y.Z
```

## Step 4 — commit the bump (1 min)

```bash
git add src/version.ts package.json server.json CHANGELOG.md
git add README.md docs/marketing/demo-60s/*.html   # only if steps below touched them
git commit -m "release: X.Y.Z"
```

## Step 5 — registry publish (10 min, immutable!)

```bash
command -v mcp-publisher || ls ~/bin/mcp-publisher   # use whichever exists
```

Expect: `✓ published io.github.AxelVerneBooks/research-scope-mcp vX.Y.Z`.
Then **re-verify independently** (do not trust the publisher's own success line).
Verified-live command form (2026-10-16):

```bash
curl -s "https://registry.modelcontextprotocol.io/v0/servers?search=io.github.AxelVerneBooks" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); \
[print(e['server']['version'], '| status:', e['_meta']['io.modelcontextprotocol.registry/official']['status'], \
'| isLatest:', e['_meta']['io.modelcontextprotocol.registry/official']['isLatest']) for e in d['servers']]"
```

Expect one row per published version, each `status: active`, and the new release
alone with `isLatest: True` (e.g. after 0.1.2:
`0.1.0 | status: active | isLatest: False` / `0.1.2 | status: active | isLatest:
True`). Note the shape: each element nests under `server` +
`_meta`, so the search endpoint (`?search=`) is the right query — a direct
`/servers/<name>` GET 404s.
**⚠ Trap #2 (hit on 0.1.2):** the cached publisher token had expired by publish
time — publish failed, the device-flow login had to be run first (code shown in
the terminal, authorized in the browser as **AxelVerneBooks**, minimal scope),
then the retry succeeded. So: if the publish line is anything other than
`✓ published`, run `mcp-publisher login github` before assuming anything is
wrong with `server.json`. The case-sensitive namespace is
`io.github.AxelVerneBooks/*`, never lowercase.

If publish fails on validation: fix `server.json`, **bump nothing** (the version
was not consumed by a successful publish), re-run `mcp-publisher validate`,
retry. Only a *successful* publish consumes a version.

## Step 6 — npm publish (only if unblocked)

```bash
npm publish --dry-run              # inspect the 10-file manifest (dist/, README, server.json)
npm publish                        # requires npm credentials (npm adduser / token in ~/.npmrc)
```

If ENEEDAUTH: **stop — report honestly, do not fake.** The CHANGELOG "### Pending"
block stays as-is; the open issue threads keep their caveat; add the attempt note
to `docs/publication/npm-status-followup-comments.md` context. Attempts are free;
false claims are not.

When it succeeds: update CHANGELOG Pending → past tense, run the B-variant
comment swap from `docs/publication/npm-status-followup-comments.md`,
`git commit -m "chore: npm publication confirmed"`.

## Step 7 — post-publish spread + ledger

```bash
git push origin main               # after successful registry publish
```

- Push **before** claiming the release anywhere public — raw GitHub files are the
  verification target for Glama/Cline/mcp.so crawlers.
- Log the row in `gumroad-tracks/trackC-mcp-kit.md` §2: date, X.Y.Z, registry
  verified (paste the version list), npm state.
- Optional: comment on still-open Cline #3028 / mcp.so #5484 using the staged
  A/B packet (`docs/publication/`), only with the new version actually live.
- `bash tools/sync_memory.sh` (session close-out / memory sync habit).

## 0.1.3+ watch-list (differs from 0.1.2)

- npm unblocked → version surfaces #7 disappears: delete the `### Pending`
  block from CHANGELOG this release, and the caveat lines from the comment drafts.
- `docs/marketing/demo-60s/demo-vertical.html` + `demo.html` still say 0.1.1 in
  the `.sub`/outro/footer — if a re-record happens on the new version, the
  capture sha256 changes with it: re-run `npm run demo:capture` (observe the
  overwrite rules in the `tools/demo-capture.mjs` header — the published
  transcript refuses overwrites without `--force`) and update every footer sha.
- If `package.json` dependencies moved: also run `npm ci && npm test` from a
  clean clone (tmpdir) at least once before publish — catches lockfile drift
  the working tree hides.
